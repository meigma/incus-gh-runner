## 2026-07-25 09:13 — Latitude canary reproduced the hot-standby delay
The maintainer authorized a disposable Latitude canary to determine whether the proof wait depends on the Catalyst colo. One hourly `c3-small-x86` host in MEX2 (`sv_7vRENk9bgadPy`) ran Incus 7.0.1, the exact deployed controller source/version (`v1.2.0`, commit `5cabfebcf6c6636fa4e117034a6850f974b883a7`), and the proof-capable VM archive from the earlier Phase 4 live manifest. The guest used Actions Runner `2.335.1`, one patch behind the Phoenix observation of `2.336.0`.

The valid hot-standby workflow was run `30165004574`, job `89696403256`, on an already connected idle VM. The proof step began at `16:07:53.4147511Z` and the following artifact step began at `16:08:42.2141434Z`, an observed wait of `48.7993923s` (49 seconds in the Jobs API). The controller opened `GetMessage` at `16:07:51.493732504Z`; the same `lastMessageID=100000041` poll ended at `16:08:41.618608928Z` after `50.124876424s`. The next poll received `JobStarted` at `16:08:42.044198141Z`, `425.589213ms` later. The signed proof's `issued_at` was `16:08:42.050013619Z`, only `5.815478ms` after callback entry. External signature/host verification passed, and the receipt identified controller `1.2.0`/`5cabfeb`, runner ID `69`, the exact Incus VM UUID, and image fingerprint.

This independently reproduces the full hot-standby delay outside Catalyst: a Latitude controller and runner exposed essentially the same 50-second empty long-poll boundary and millisecond callback-to-proof time. The Catalyst colo/Incus host/network path is therefore not required for the symptom. The narrow behavior remains in the GitHub scale-set message path or pinned client semantics, not local proof generation.

## 2026-07-25 09:42 — Five-second A/B canary isolates the message-poll boundary
After the maintainer approved proceeding, implementation work moved to the isolated Worktrunk branch `feat/job-proof-message-diagnostics` at commit `921ee6ff847c8482c07bfc1534143215ec008755`. The local patch adds secret-safe `GetMessage` start/completion timing, sanitized message-type counts, `JobStarted` queue/assignment timestamps, and a deliberately narrow non-YAML canary switch (`INCUS_GH_RUNNER_DIAGNOSTIC_SHORT_POLL=1`). The wrapper translates only its own five-second `context.DeadlineExceeded` into the upstream client's documented empty result; parent cancellation, unrelated transport errors, and upstream errors remain failures. No production or Phoenix state was changed.

Focused race tests passed for `./internal/adapters/github`, `./internal/provenance`, `./internal/runtime`, and `./internal/app`. The complete `mise exec -- moon run root:check` gate passed after clearing a stale golangci-lint cache that referenced a removed sibling worktree. The first gate attempt had already passed build, tests, formatting, release checks, and docs; only the stale cache polluted lint output.

A second disposable Latitude `c3-small-x86` host in MEX2 (`sv_Yx2za1e9naVrL`) used the same proof-capable image fingerprint `f7a0f28e9914ef475216f9bf6800f08d37582a7956f8ab3ac025a36bb183c411`, the same persistent test scale set, and the same workflow for a controlled hot-standby A/B comparison.

Baseline run `30166003024`, job `89699019984`, used normal upstream long polling. The workflow proof wait was `47.8395333s`. A poll that began at `16:37:32.617459289Z` returned empty after `50.113239099s`; the next poll returned the `JobStarted` message in `149.560077ms`. The event reported `runnerAssignTime=16:37:32.444015751Z`, while callback entry was `16:38:22.975129060Z`, a `50.531113309s` gap. The signed proof was issued only `5.704916ms` after callback.

Canary run `30166076210`, job `89699212952`, differed only by the five-second diagnostic poll bound. The workflow proof wait fell to `2.0891212s`. The poll after assignment expired after `5.001248943s`; the next poll returned `JobStarted` in `133.513989ms`. The event reported `runnerAssignTime=16:39:53.077064531Z`, while callback entry was `16:39:58.478991631Z`, a `5.401927100s` gap. The signed proof was issued `5.052341ms` after callback.

The causal shift matches the poll bound: shortening the client-visible boundary from approximately 50 seconds to 5 seconds shortened `runnerAssignTime`-to-callback delivery by approximately 45 seconds. In both cases the current in-flight request failed to return `JobStarted`, and the immediately following request received it in about 0.13–0.15 seconds. This rules out a fixed approximately-50-second late publication interval and isolates the behavior to the GitHub scale-set message service's handling of in-flight `GetMessage` requests (or undocumented endpoint semantics), not Incus, the Catalyst colo, proof generation, or local callback processing. The pinned `actions/scaleset v0.4.0` client follows its documented long-poll loop; it has no newer release or supported poll-duration setting.

The signed receipts independently verified controller commit `921ee6f`, runner IDs 72 and 73, each exact Incus UUID, and the expected image fingerprint. Evidence is under `build/job-proof-short-poll-20260725/evidence/`; its checksum-manifest SHA-256 is `942081949ac362fccb12b563700138b93625f2d43d10f90ec31a646abd514db9`, and a targeted sensitive-pattern scan passed. The second Latitude host, test runner IDs 72–74, owned VMs, remote credentials, and the local ephemeral private key were removed. Teardown was verified by a Latitude 404 lookup, an empty project server list, an empty test-runner selection, and zero owned instances.

## 2026-07-25 10:00 — Configurable long-poll reset workaround
The maintainer submitted the upstream report as [actions/scaleset#122](https://github.com/actions/scaleset/issues/122), then authorized a temporary controller-side workaround. The existing diagnostic patch was promoted into the opt-in `github.message_poll_timeout` duration setting on the same implementation branch. The matching environment binding is `INCUS_GH_RUNNER_GITHUB_MESSAGE_POLL_TIMEOUT`; the earlier hidden `INCUS_GH_RUNNER_DIAGNOSTIC_SHORT_POLL` switch was removed so there is one documented control surface.

The default remains `0s`, preserving the pinned upstream client's approximately 50-second long poll. A nonzero value must be at least `5s`. When the controller's own child-context deadline expires, only that `context.DeadlineExceeded` is translated into a healthy empty poll so the listener immediately opens the next request. Parent cancellation, transport failures, and unrelated upstream errors still propagate normally. Startup emits a warning when the override is active.

Configuration loading, exact YAML validation, environment binding, runtime wiring, the packaged systemd example, and the configuration reference were updated. The documentation identifies the setting as a temporary workaround for issue #122 and notes that `5s` can generate up to approximately 12 idle message requests per minute instead of approximately 1.2 with the upstream long poll.

Focused race tests passed for `./internal/config`, `./internal/adapters/github`, and `./internal/runtime`. The complete `mise exec -- moon run root:check` gate passed, including formatting, lint, tests, build, release configuration, and documentation build. The implementation is checkpointed locally as `977b6ed8d96020c130e8d255f5caec7f9739b224` (`feat(github): configure message poll timeout`). The code branch remains unpushed, and no deployment or production configuration was changed.
